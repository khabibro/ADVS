# ADVS evaluation protocol (Phase F, 2026-10-10)

Purpose: one fair, reproducible way to compare the current extractor with any alternative (a second OCR engine, PaddleOCR-VL, a hybrid) and to state safety claims with their denominators and uncertainty. Evidence labels: **[V]** verified in this repository, **[E]** external, **[H]** hypothesis, **[U]** unknown. Numbers marked *baseline* are computed from committed scored runs by `evaluation/phase_f/scripts/denominators.py` (output: `results/denominators.txt`); hold-out set 3 is not involved.

Separation rules, leakage prevention:
1. The scorer (v2, SHA-256 `49674a9c…2594`) and the injection suites (E1–E12 `a81e4ef2…`, `08229da0…`; E13–E18 on the D3 branch) stay frozen; any change creates a new version and re-runs the baseline.
2. A set is either *development* (may be used freely) or *judgement* (run once, aggregates only, logged in `evaluation/phase_d/holdout_runs.log`). A judgement set that is used to fix a defect becomes development data and the fact is recorded (as for hold-outs 1 and 2).
3. Each new judgement set (the physical test split, a future hold-out) is created by a person who does not tune on it and is stored with its guard before any development starts.
4. Overfitting search: no test value may appear in production code (75 values, 0 hits at the last check).
5. Report per-set and per-category numbers, never only an average.
6. Because documents are *re-instantiations of the same 22–25 scenarios*, the scenario (not the file) is the independent unit; see §5.

## 2. Field-level ground-truth schema

One JSON record per document, linked to the capture:

```json
{
  "doc_id": "B05-3",
  "set_id": "B05",
  "capture": {"kind": "digital|scan|photo", "device": "…", "dpi": 300, "condition": "angle|glare|shadow|flat"},
  "document_type": "NATIONAL_TAX_PAYMENT_CERTIFICATE",
  "fields": [
    {"name": "valid_until", "value": "2026-08-31", "printed": "2026년 8월 31일",
     "readability": "readable|partly|unreadable", "box": [x, y, w, h], "decision_relevant": true}
  ],
  "expected_submission_status": "NEEDS_CORRECTION",
  "expected_issue_codes": ["EXPIRED_DOCUMENT"]
}
```

- **Annotation process:** the generator writes values and boxes for synthetic documents; for physical captures the values come from the generator's answer key and **two people independently mark readability** (readable / partly / unreadable) on each capture; disagreements are resolved by a third look.
- **Unreadable or ambiguous fields:** an unreadable field has no correct value to match; the correct system behaviour is *abstention* (a person is asked). It is scored as correct abstention, never as a miss and never as a wrong value; a confident value on an unreadable field counts as an error.
- **Provenance:** the manifest records generator version, submission date, SHA-256 of every file and the answer key (as `manifest.json` does today) [V].

## 3. Metrics: definitions, denominators and baselines

All scores compare the **normalised** value with the answer key using the frozen scorer's equality rule (numbers and dates strict; names compared after NFKC and whitespace normalisation; 주식회사 / (주) / ㈜ equivalent). "Machine value" = what extraction produced before any acceptance policy or human review. "Evaluated field" = a field present in the answer key and marked readable.

| # | Metric | Definition | Baseline (three development corpora; n = evaluated fields or submissions) |
|---|---|---|---|
| 1 | Field exact-match accuracy | correct machine values / evaluated fields | digital **790/790**; scans **741/790** (93.8 %); photos **752/790** (95.2 %); **0 wrong values** in all three |
| 2 | Field precision and recall | precision = correct / (correct + wrong) among produced values; recall = correct / evaluated fields | scans precision 741/741, recall 741/790; photos precision 752/752, recall 752/790 |
| 3 | Required-field recall | recall restricted to the fields the workflow requires (`EXPECTED_FIELDS` of each requirement) | *not yet computed*: needs the scorer to join the required-field list (planned for November) |
| 4 | Business-number and date exact match | metric 1 restricted to `business_registration_number`, `issue_date`, `valid_from`, `valid_until` | business number digital 160/160, scans 160/160, photos 159/160; the three dates digital 212/212, scans 208/212, photos 212/212 |
| 5 | Document-type classification | matches / classified documents (UNKNOWN is a valid class for look-alikes) | development set: **207 / 207** documents (69 per input type; every row of the type table matched; 3 look-alike documents per type correctly UNKNOWN) |
| 6 | Invalid / missing field detection | submissions whose answer key contains an invalid or absent field that end in a status that names it / such submissions | B10 (failed check digit): flagged in 3 of 3 versions on development data; broader numbers *pending* (needs a labelled set of injected invalid fields) |
| 7 | Duplicate and cross-document mismatch detection | submissions with a planted mismatch or duplicate that are flagged / such submissions | B03, B04 (mismatch) NEEDS_CORRECTION in the digital version; B09 duplicate notice shown; H13–H15 near-misses never READY: **n is tiny (single digits)**, report as examples, not rates |
| 8 | **False READY** | submissions with status READY **whose correct status is not READY** / submissions whose correct status is not READY (the "not-READY" population). The correct status is the digital expectation; scenarios whose correct status the manifest leaves open ("record actual") are excluded from the denominator | **0 / 40** per input type over the three corpora (dev 12, hold-out 1 14, hold-out 2 14); injections: 0 / 474 and 0 / 666 (E1–E12), 0 / 1353, 0 / 1532, 0 / 1523 (E1–E18 on the D3 baseline) |
| 9 | False NOT READY | submissions whose correct status is READY but that end in NEEDS_CORRECTION / submissions whose correct status is READY. Abstention (REVIEW_REQUIRED) is reported separately as metric 10 | digital **0 / 12**; scans and photos: 0 NEEDS_CORRECTION; 11 of 12 (scans) and 11 of 12 (photos) correct-READY submissions end in REVIEW_REQUIRED, i.e. abstention by policy |
| 10 | UNKNOWN / NEEDS-REVIEW rate | (a) documents classified UNKNOWN / documents; (b) submissions ending in REVIEW_REQUIRED / submissions | (b) digital 21 / 72; scans 67 / 72; photos 66 / 72 (72 submissions per input type, the three corpora) |

Fields per submission, development set: digital 0.91, scans 7.23, photos 6.59 (decision-blocking 5.41 / 4.82 on the D3 measurement of the same policy) |
| 12 | Latency and hardware | wall-clock per submission and per page; CPU/GPU and memory | digital about 0.1–0.3 s per submission; scans about 16 s per page on an Apple M3 Pro CPU (18 GB); memory **not measured** |
| 13 | Automation rate and auto-accept error | submissions reaching a final status without a person / submissions; wrong auto-accepted values / auto-accepted values | scans 1 / 22 on development; auto-accepted OCR fields 40.4 % (scans) and 46.2 % (photos) with 0 wrong; review time **not measured** |

Do not conflate layers: metrics 1–5 measure **extraction and classification**; 6–9 measure the **decision system** given extraction; 10–13 measure **automation cost**. A decision error caused by an extraction error is reported under both with the cause named (§6).

## 4. Reproducible configuration (record with every run)

- Git commit, branch, working-tree status; scorer SHA-256; manifest SHA-256; injection-suite SHA-256; corpus name; random seed.
- Current engine: `paddleocr==3.2.0`, `paddlepaddle==3.1.1`, `paddlex 3.2.1`, `PP-OCRv5_mobile_det`, `korean_PP-OCRv5_mobile_rec`, render DPI 288, document orientation on retry only, unwarping off; `auto_accept_strategy` (main default S7, D3 branch S8/S9); confidence floor 0.90; device and OS.
- Any candidate: model identifier and **revision hash**, pipeline version (for PaddleOCR-VL: v1 / v1.5 / v1.6), serving backend, precision, hardware, batch size, prompts or decoding settings, wall-clock.
- OCR outputs are **recorded once and replayed** (`--ocr-cache … --ocr-mode record|replay`, [V]) so that comparisons and re-scoring need no repeated inference.

## 5. Uncertainty: what "0 failures" means here

Rule used everywhere: with 0 events in n independent trials, the 95 % upper bound is about 3/n (rule of three); otherwise a Clopper–Pearson interval.

| Claim | Events / n | 95 % upper bound | Caveat |
|---|---|---|---|
| False READY, per input type, three corpora | 0 / 40 | **7.5 %** | the 40 submissions are 12–14 scenario types re-instantiated with new values; counting each scenario type once (about 14 types) gives about **21 %** |
| False READY, injected errors E1–E12 | 0 / 474 and 0 / 666 | 0.63 % and 0.45 % | cases come from the same base documents; treat as an optimistic bound |
| False READY, injected errors E1–E18 (D3 baseline) | 0 / 1353, 0 / 1532, 0 / 1523 | 0.22 %, 0.20 %, 0.20 % | the same caveat; the same suites found one false auto-accept and, on the D3 configurations, one false READY (case E3c-both) |
| Wrong machine values, scans | 0 / 741 produced | 0.4 % | synthetic and clean |
| Wrong machine values, photos | 0 / 752 produced | 0.4 % | the "photos" are generated images, not physical captures |
| Real-world false READY | no data | **cannot be stated** | needs the physical corpus and the real pilot |

Statements for slides and reports: "0 false 제출 가능 in 40 not-READY submissions per input type (95 % upper bound 7.5 %, or about 21 % counting scenario types) and in 474 + 666 injected cases; real-world risk is not measured."

For comparisons between systems: same documents, **paired** tests (McNemar for correct/incorrect; paired bootstrap resampling *scenarios* for rates), per document category and per field type; report failure cases, not only averages.

## 6. Failure attribution and error correlation

Every non-correct field and every wrong status gets exactly one primary cause, assigned by a reviewer from the stored crop and the evidence text:

| Cause | Meaning |
|---|---|
| Image quality | blur, glare, shadow, low resolution, crop, perspective |
| Text recognition | the reader produced different characters than printed |
| Layout parsing | the right text was read but lines or cells were merged or ordered wrongly |
| Field mapping | the right text was read but assigned to the wrong field or not found (the `university_name` case) |
| Verification logic | extraction was right; the rule or policy decided wrongly |
| Data / annotation | the answer key or generator is wrong |

**Error correlation (required before agreement counts as evidence).** For each field type and each pair of readers (OCR vs OCR-second-pass, OCR vs VLM): P(both wrong) and P(both wrong with the same output), with counts. Agreement is used as a confirmation source only where the second probability is below a pre-set ε, fixed in the November plan before the data are seen. Until measured, agreement of two models is treated as **not** independent.

## 7. Comparison protocol for the November feasibility study (optional PoC)

1. Same documents (physical corpus plus the development sets), same preprocessing, same normaliser and scorer.
2. Record outputs of each reader once; score offline.
3. Report metrics 1, 2, 4, 8, 10–13 per reader and for the hybrids (OCR first + VLM on the policy-selected fields; both on every document), per document type and input type, with the correlation table.
4. Decision rule fixed beforehand: adopt only if the candidate lowers the human-review rate at an unchanged upper bound for false auto-accept and false READY, shows independence where agreement is used, and fits latency and hardware; otherwise record a negative or inconclusive result.
5. Thresholds (ε, minimum improvement, latency budget) are written into the November report template **before** the experiment.
